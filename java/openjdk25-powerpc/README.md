# OpenJDK 25 PowerPC review package

Targets Darwin 9: PPC32 Zero and PPC64 G5 HotSpot. The source baseline is
`1775ea114f649f0314e4e43eb6c802ff16dfab7c` (`jdk-25.0.5.0.2-ga`).

## Integrated dependencies

The source patch builds `libosxcompat` inside java.desktop for both architectures.
JNF/JRS implementations and headers were recovered from the working Java 8 tree,
`jdk/src/macosx/native/compat`. They replace the previous copied binary dependency.
No external JNF/JRS framework directory or compatibility-library path is needed.
This preserves the existing compatibility implementation; it does not establish
complete equivalence with Apple's native UI and accessibility frameworks.

The Portfile builds checksum-pinned libffi 3.8.0 privately as a static library for
the Zero variant. It does not change the system libffi installation.

Architecture-specific JDK 25 bootstrap archives are hosted at
`https://powerpc-ports.org/distfiles/openjdk25/bootstrap-2/`. MacPorts downloads,
verifies and extracts them as distfiles, rather than installing a separate port. Both contain javac, jar, jlink, jmod, JMODs and the locale-data module needed by the native build.
Compiler runtime libraries and relocatable paths are included in the JMODs so
images generated by the bootstrap can execute without post-link repairs.

PPC64 also downloads checksum-pinned GCC 14.3 support archives from
`https://powerpc-ports.org/distfiles/openjdk25/native-build-support-1/`.
These supply the missing 64-bit compiler libraries when the installed compiler
is PPC32. They are linked statically into the JDK; installed 32-bit runtimes are
not replaced. The source archive and original cross-build recipe are published
beside the support archive. Build tools can run in either supported bitness.

## Installation

From this directory on Leopard, with GCC 14 and the declared build dependencies:

```sh
sudo port install configure.build_arch=ppc64 +server
```

For PPC32, use `configure.build_arch=ppc +zero`. No manual bootstrap or bridge
options are required. The native build uses the full `images` target. Set
JAVA_HOME to `${prefix}/Library/Java/JavaVirtualMachines/openjdk25-powerpc.jdk/Contents/Home`.

## Validation

- Full PPC32 and PPC64 cross-compiled `images` builds pass.
- A native PPC64 G5 `port install` completed and activated
  `openjdk25-powerpc @25.0.5.0.2_0+server`.
- The installed JDK passes Java 25 runtime features, virtual threads, scoped
  values, record patterns, file attributes, 100,000 compiled byte-order
  operations, and 20,800 array-copy overlap/zero/tail cases.
- The installed desktop bridge renders text with valid metrics and 688 ink pixels.
- Debugger-agent startup, javac/JAR/JMOD creation, jlink and execution of the
  generated runtime all pass.
- All 71 installed Mach-O binaries are PPC64. Their dynamic dependencies are
  internal JDK libraries or Apple system libraries, with no build-tree paths.
- Both original bootstrap architectures pass native compile/JAR/JMOD/jlink/run
  and headless text rendering. Bootstrap-2 PPC64 also passes the previously
  failing Thai break-iterator generator.
- The hosted bootstrap archives pass full HTTPS-download checksum verification.
  MacPorts fetches and checksums the versioned PPC64 archive successfully.
- Portfile lint reports zero errors and warnings. The source patch is checked
  against the pinned upstream files and compared byte-for-byte with the source.

Native testing exposed and fixed Leopard xattr option differences, missing ADLC
integer-limit definitions, unsupported codesign options, a missing bootstrap
locale module, MacPorts search-path contamination, and missing GCC JVM loader
paths. GCC now selects matching SDK iconv headers and library. MacPorts compiler
search-path defaults are disabled for this port, preserving bundled libraries.

The native install test reused existing build dependencies and resumed after
fixes. It did not validate a full dependency upgrade or a native PPC32 install.
Its workspace was on an external volume, with sandboxing disabled for that
invocation because MacPorts mishandles the plus sign in the volume name.
The Portfile does not disable sandboxing.

The binary archives belong in release storage, not the ports Git repository.
No jtreg/TCK certification is claimed. Zero virtual threads use native threads
rather than multiplexed continuations. Changes are unstaged.
